# 团队分工与接口协作

## 文件归属

| 负责人 | 默认负责的文件 |
| --- | --- |
| 你 / 整合负责人 | `app.*`、`project.config.json`、`config/`、`services/`、`components/`、公共资源、检查脚本与后端 |
| 队友 A | `pages/companion/`；后续新建聊天、连续会话、录音与播放模块 |
| 队友 B | `pages/observation/`、`pages/records/`、`pages/profile/`；观察流程、记录详情、账号界面 |

初期由整合负责人维护公共组件和配置。更改共享接口时，先约定参数和返回数据，再由整合负责人修改公共层；避免三人同时修改 `app.json` 和 `services/api.js`。

## 推荐协作流程

1. 骨架先在 Windows 开发者工具中编译，通过后由整合负责人提交为团队共同起点。
2. 每人从同一个骨架提交新建功能分支，例如 `feature/mobile-companion`、`feature/mobile-observation`。
3. 一次提交只做一个明确功能，通过 Pull Request 合并，附改动说明和预览截图。
4. 提交前运行 README 中的检查，并根据修改范围做真机验证。
5. 账号资料、模型密钥、录音、观察结果和本地开发工具偏好不提交。

不要共享微信登录态。每个人以自己的开发成员账号登录工具，并使用本项目同一个 AppID。

## 首轮任务

- A：完善陪伴页的竖屏布局；在现有单轮真实问答上接连续会话，再接录音、转写、播放与停止。优先处理重复点击、请求中断和键盘遮挡。
- B：接入真实 WAV 录音、后端正式知情同意、上传和任务创建；完善任务轮询、报告详情及登录界面。不要把当前的示例占位当作音频提交。
- 整合负责人：提供可达的后端地址和接口样例；维护公共错误处理；核对录音格式；合并代码并整理版本说明。

## 完成标准

功能必须能从入口完整走通，失败时给出明确反馈。演示状态要可见；只在真实请求成功时显示成功。真实功能尚未接入的按钮应说明其当前状态。

## 骨架检查记录

源码与业务逻辑可在 Ubuntu 检查；微信开发者工具编译、Android/iOS 录音、播放和键盘行为由对应平台实测并记录。不要把 Node.js 检查结果写成“微信真机已通过”。
